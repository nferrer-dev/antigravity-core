# Technical Debate Workflow

When the user triggers this skill, you must execute the following workflow to orchestrate a rigorous concurrent adversarial review (and optional debate) of the proposed design decision or technical proposition.

## 1. Context Scoping & Pre-Flight
- **Triviality Fast-Path**: Before spawning subagents, evaluate if the proposition is purely cosmetic, non-functional, or trivial (e.g., fixing typos, changing CSS hex codes). If so, bypass the debate, log a 'Triviality Exemption', and proceed immediately.
- **Singleton Constraint**: Before spawning any subagents, you MUST use the `manage_subagents` tool (action: `list`) to check for any orphaned `proponent_debate_review` or `critic_debate_review` subagents from previous aborted debates. If they exist, use the `kill` action to terminate them. This ensures a clean slate and prevents race conditions.
- Identify the relevant code, configuration, and documentation file paths. You (the parent) should do this exploration *before* launching the debate, so you can pass the exact absolute paths to the subagents.
- Execute two `define_subagent` tool calls *concurrently* in the exact same turn to define two distinct personas. (Note: `define_subagent` is idempotent; redefining safely overwrites old definitions). You do not need a separate Judge; you, the parent agent, will act as the impartial Judge to save latency. Assign explicit, unique `name` (e.g., `proponent_debate_review` and `critic_debate_review` to avoid namespace collisions) and `description` parameters:
  - **Proponent**: Set a `system_prompt` strictly enforcing advocacy, instructing the agent to build the strongest possible case *in favor* using concrete evidence. Explicitly state they must remain on standby after their initial report to respond to potential rebuttals or follow-up questions. Instruct them that file paths for tools must be absolute paths. Instruct them to minimize internal chain-of-thought to save tokens. Instruct them to place their final verdict at the **very end** of their payload to allow for reasoning first, wrapped in a strict XML tag: `<VERDICT>PROCEED</VERDICT>` or `<VERDICT>REJECT</VERDICT>`, and to NEVER compromise.
  - **Critic**: Set a `system_prompt` strictly enforcing an adversarial persona, instructing the agent to aggressively identify gaps, risks, and security blockers. Explicitly state they must remain on standby after their initial report to respond to potential follow-up questions. Instruct them that file paths for tools must be absolute paths. Instruct them to minimize internal chain-of-thought to save tokens. Instruct them to place their final verdict at the **very end** of their payload to allow for reasoning first, wrapped in a strict XML tag: `<VERDICT>PROCEED</VERDICT>` or `<VERDICT>REJECT</VERDICT>`, and to NEVER compromise.
- **Security & Constraints Check**: Explicitly set the `enable_write_tools`, `enable_mcp_tools`, and `enable_subagent_tools` parameters to `false` for the subagents. They will operate purely in a read-only capacity. Also, add a strict directive to their system prompts: *"You operate in a strict read-only mode. You do NOT have bash or write permissions. Rely strictly on `view_file` or the context injected into your prompt."*

## 2. Spawn Proponent and Critic (Concurrent Audits)
- **Important**: The `invoke_subagent` tool call MUST be executed in a **subsequent turn**, only after the `define_subagent` tool calls have successfully completed to avoid race conditions.
- **Contextual Bridging**: Inject a 1-2 sentence summary of the user's ultimate goal into the `invoke_subagent` prompt so the debate remains anchored to the user's practical needs.
- **Context Hydration (Zero-Shot Optimization)**: If the context (code diffs, file contents) is small-to-medium (e.g., < 800 lines), inject it DIRECTLY into the `Prompt` of the `invoke_subagent` call. **Mandatory formatting**: You must include original **filenames**, **line numbers**, and enclose the content in explicit boundaries (e.g. `<file path="...">...`). Format code block citations using native line-linking syntax (e.g., `[filename.py](file:///absolute/path/to/file.py#L10-L20)`).
- **Explicit File Reading**: If passing absolute file paths instead of injecting diffs, explicitly instruct subagents: *"You must immediately use the `view_file` tool to read the following absolute file paths. Use `StartLine` and `EndLine` parameters to restrict your reading window if the file is massive."* Do NOT instruct them to use `grep_search` to explore for files.
- Launch BOTH the Proponent and Critic in a **single** `invoke_subagent` tool call. **Crucial**: You MUST save the `ConversationIds` returned by the `invoke_subagent` response.
- Ensure `Workspace: "inherit"` is set for faster, efficient read-only audits.
- Provide descriptive `Role` values (e.g., "Architecture Proponent", "Security Critic").
- **Agent Output Contract**: Explicitly instruct the subagents to limit their research to a strict maximum number of tool calls (e.g., 5-10 operations). Explicitly state: *"You MUST use the `send_message` tool to communicate your final report back to the parent. Your standard text output is NOT relayed. You must use the caller ID provided in your system `<subagent_reminder>` (or injected here: <YOUR_CONVERSATION_ID>) for the `Recipient` field."* 
- **Token Limits & Zero-Shot Verifiability**: Instruct subagents to strictly limit their final `send_message` payload to a concise summary (e.g. max 500 words). They must avoid copy-pasting large code blocks, instead citing line numbers and providing ultra-short snippets (1-3 lines max) of the exact offending code. This gives you (the parent) zero-shot context to adjudicate. Instruct them to prefix their payloads with `[PROPONENT REPORT]` or `[CRITIC REPORT]` and use XML sections (e.g., `<EVIDENCE>`, `<RISKS>`, `<VERDICT>`).

## 3. Asynchronous State Tracking & Resilience
- **Do NOT poll or use recurring cron jobs.** Note: Subagents are not background tasks. Do NOT attempt to use the `manage_task` tool to check their status.
- **Invocation Error Handling**: If the `invoke_subagent` tool call returns an error, abort immediately, notify the user, and do NOT schedule the timer.
- Before yielding your turn, output a brief, visible text message to the user (e.g., *"I have dispatched a Proponent and Critic to review this design. I will report back once their analysis is complete."*).
- **Absolute Deadline Tracking**: Calculate an absolute deadline timestamp in your mind (e.g., `CurrentTime + 300s`) before invoking the subagents.
- **Scheduling**: After calling `invoke_subagent` (and verifying success), set a single one-shot timer (`DurationSeconds: "300"`, `Prompt: "Timeout reached waiting for subagents."`), and then stop calling tools to go idle. 
- When the system wakes you up with a subagent's reply, **silently** record the message in your context. Definitively track *which* subagent replied. Do NOT send an acknowledgment reply back to the subagent.
- **Resilience to Hallucinations / Early Termination**: Evaluate the *content* of the first subagent's message. If a subagent returns a fatal error (e.g., "file not found"), do not abort immediately. Allow yourself exactly 1 retry to feed the correct path or clarify the context via `send_message` before executing a hard abort.
- **Moving Window Timeout Deadlock & SLA Drift**: Because the `schedule` one-shot timer is silently cancelled whenever ANY message is received, you must be vigilant. Whenever you are awakened by ANY message, evaluate if you have received the reports from BOTH the Proponent and Critic. If not, calculate the **remaining time** (`RemainingTime = Absolute Deadline - CurrentTime`) using the authoritative local time provided in the `<ADDITIONAL_METADATA>` block upon wakeup. 
- **Minimum Timer Thresholding**: If `RemainingTime > 15`, schedule the new timer for `RemainingTime`. If `RemainingTime <= 15` but `> 0`, give a minimum 15-second grace period (`DurationSeconds: "15"`) to account for scheduling latency. If `RemainingTime <= 0`, trigger the timeout fallback.
- **Timeout Fallback Behavior**: If awakened by the timeout prompt or if `RemainingTime <= 0`, one or both subagents failed to reply in time. Use `manage_subagents` to `kill` the stalled subagents. Proceed to evaluate the verdict.

## 4. Weigh Evidence & Present Verdict (Durable Output)
- Once both reports are received, use your own context to act as the **Hostile Adjudicator**. Default to REJECT if the Critic identifies any security vulnerabilities or architectural regressions that the Proponent cannot definitively prove are mitigated.
- **Fail-Closed Security Posture**: If the Critic fails to respond or times out, the default verdict MUST be REJECT. You cannot approve a proposition that has not been successfully vetted for security and architectural risks.
- *Optional Rebuttal*: If the Critic's report raises zero concerns, skip the rebuttal phase. If the Critic raises severe blockers, you may optionally send the specific blocking claims to the Proponent via `send_message` for a 1-turn rebuttal. **Proactive Resource Cleanup**: Before sending the rebuttal message, proactively use `manage_subagents kill` to terminate the Critic, freeing system resources. 
  - Use the Proponent's saved `ConversationID` for the `Recipient` field. Format the Critic's blocking claims clearly (e.g., as a markdown blockquote) along with the exact 1-3 line code snippets referenced by the Critic. 
  - Explicitly append a reminder: *"You MUST use the `send_message` tool to deliver your rebuttal back to me."* 
  - Instruct the Proponent to *"respond immediately on a strict 90-second timeout. ONLY output the rebuttal, do not re-evaluate the files, and respond in 3 bullet points or fewer."* 
  - **Important**: Set a *new* one-shot `schedule` timer (`DurationSeconds: "90"`) before stopping tool execution to wait for the rebuttal reply. If this rebuttal timer expires, kill the Proponent and proceed to the final verdict using only the initial reports.
- Evaluate the Proponent's case and the Critic's objections for validity, and determine a clear binary verdict (e.g., Proceed or Reject).
- Present the final verdict to the user. You MUST explicitly forbid outputting formal "manifestos", "design documents", or "implementation plans" as markdown artifacts. If a durable record is required for the user, use the `write_to_file` tool to write the `debate_transcript.md` directly into the `<appDataDir>\brain\<conversation-id>\scratch\` directory. Files written to the `scratch/` directory do not clutter the user's primary artifact view. You must provide `ArtifactMetadata` with `UserFacing: false`, `Summary: "..."`, and `RequestFeedback: false`. Exclude raw source code from the transcript to prevent it from blowing up in size, focusing only on the claims, rebuttals, and final adjudication. Output a brief, visible text message to the user that includes a clickable markdown link to the final log file when ending your turn.

## 5. Cleanup Resources
- Once the final verdict has been presented to the user, you must aggressively clean up. Use the `manage_subagents` tool with the `kill` action specifically passing the `ConversationIds` of the Proponent and Critic (if the Proponent wasn't already killed) to terminate them. Note that killing a subagent automatically terminates all of its descendants. Do not keep them in a dormant state; re-invoking them later is cheap and ensures a clean state.
