Ah! I discovered exactly why you didn't see a difference.

The initial logic I wrote to check for the active chat (parentA.className.includes(...)) was throwing a JavaScript TypeError under the hood if it encountered certain SVG elements or links without a className string. Because the Phone UI's server.js evaluates this strictly, the entire /chat-history API call was crashing and returning Context failed.

When the Phone UI fails to fetch new history, it silently falls back to its cached history—which means you were just looking at the old history list that didn't have the isActive data attached to it!

I've just pushed a fix to master that:

  1. Uses classList.contains() instead, which is strictly safe against SVG type errors.
  2. Checks for data-active="true" and aria-current="page" as well to be absolutely certain it catches the active state.
  3. Wraps the logic in a try/catch block so that even if one element fails, the rest of the history still loads flawlessly.

The server has been restarted. Could you try opening the history drawer one more time (and maybe do a quick pull-down-to-refresh if your phone browser supports it)? It should successfully pull the fresh history now and grey out the active chat!
